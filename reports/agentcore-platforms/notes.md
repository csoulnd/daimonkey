## 开场（约 1.5 分钟）

各位好。这次汇报的对象是两家同名产品：阿里云 AgentCore 和 Amazon Bedrock AgentCore。

先说为什么研究它们。企业要把 Agent 用起来，迟早撞上同一组问题：谁能调用、跑在哪、状态怎么恢复、权限怎么管。两家厂商官方文档的出发点是一致的——**把 Agent 从「跑得起来」带到「管得起来」，进入受治理的运行环境**。

但同一个命题，两家给出了完全不同的解法。今天的汇报分四段：先看阿里云怎么解，再看 Amazon 怎么解，然后对比，最后跳出产品，提炼这类平台的**核心能力检查表**。研究基线是 2026-10-10 的官方文档，未做部署实测；页面上的「研究判断」都按本文档口径标注。

## 第一章：阿里云 AgentCore（约 3.5 分钟）

阿里云的解法一句话是：**统一组织，先管理、后运行**。

官方把它定位成智能体构建和治理平台。注意它的核心对象不是「一个 Agent」，而是 Workspace、Agent、Team、实例、Session 这一组资源——**平台的第一件事是把多来源的 Agent 管理起来**，运行反而是第二位的。

[指向系统关系图] 看这张研究视图：左边是渠道和 Agent Endpoint，是「进来」的部分；上面 Workspace 和 Team 通过「配置与授权」「任务与组织」作用在 Agent 定义上——**这是管理面**；中间往下才是运行面：托管实例与 Session 承载会话，QwenPaw／Qoder 或高代码应用负责执行循环，再往下接模型、Skill 与 MCP、工作目录与 OSS。AgentLoop 观测横向采集执行轨迹。

点开任意组件可以看到它的职责说明——这些说明直接引自调研文档，不是我们另写的。

这里有两个关键判断要讲清楚：

第一，**统一管理界面不等于执行语义一致**。托管 Harness、高代码部署、本地纳管是三条路，责任边界不同；比如托管 Harness 当前模式就有明确限制：知识库与长期记忆、工具审批，指南里写明暂不支持。

第二，**对象生命周期的拆分值得借鉴**：Workspace 管资产、Agent 是执行单元、实例承载进程、Session 组织交互——这是「资源组织」和「运行组织」分开的设计，我们自建平台时可以直接借用这个拆分。

## 第二章：Amazon Bedrock AgentCore（约 3.5 分钟）

Amazon 的解法一句话是：**可组合运行，先运行、按需治理**。

官方定义是 Agent 构建、部署和运行平台。它的核心不是「管理一批 Agent」，而是**把 Agent 需要的运行能力拆成一排服务原语**：Runtime、Memory、Gateway、Identity、Browser、Code Interpreter、Observability——按需组合，不是逐层穿过的七层栈。

[指向系统关系图] 同样的读法：调用方进 Runtime Endpoint，进到托管运行环境；里面是两条路——**托管 Harness（Strands 驱动）或者你自己的 Agent 代码**；往下接模型服务和工具与记忆服务，最终落到 Gateway、Browser、Code Interpreter、Memory 这些具体原语。Identity／Policy 管权限，Observability 采集评估，都是横向的。

这里的关键判断：

第一，**Runtime 框架中立，但 Harness 不中立**——Harness 固定用 Strands 驱动。两条路共享运行平台，但自由度和责任不同：选 Harness 少写循环、接受它的编排边界；自带代码自由度大、自己处理服务间契约。这是选型的第一分水岭。

第二，**服务可组合既是能力也是责任**。复用空间大，但身份、状态、故障契约要应用自己协调——平台服务各自可靠，推不出它们和你的业务系统有联合事务。

第三，状态与生命周期按计算模式分：microVM 与 Instances 的隔离和时限边界不同，会话上限分别约 8 小时和 14 天——这是模式限制，不是 SLA。

## 第三章：对比（约 3 分钟）

把两家放在一起，差异集中在三处。

**第一，组织哲学**。阿里云突出 Workspace 资源组织与 Agent／Team 管理，把 Agent 生态当企业资产；AWS 突出可独立采用的服务原语，把运行能力做成积木。一个从「管理」出发，一个从「运行」出发。

**第二，承载方式**。注意两家都有「托管循环」和「自带代码」两条路，但 Harness 和 Runtime 的关系不同：AWS 的 Runtime 对框架中立、Harness 只是其中一个消费者；阿里云的托管 Harness 是平台能力的一部分，引擎固定为 QwenPaw／Qoder。比较时应该按模式分别比，**不能用同一「功能数」比较不同职责的产品**。

**第三，边界与代价**。这是最容易踩坑的地方：托管不是一句话，平台托管进程、托管循环、托管状态、托管整个业务事务是四个不同承诺。恢复语义要拆开验证——历史、文件、检查点、外部副作用各自能不能恢复；用户批准一次外部写入后进程崩溃，最终写入是否重复，**取决于工具幂等和业务系统，而不是「有记忆、有沙箱」**。

所以这张对比表的用法不是评谁强，而是**拿到选型验证清单**。

## 第四章：架构提炼（约 3 分钟）

最后跳出产品。把这批调研的分析框架抽出来，就是这类平台绕不过去的**七个问题**——注意，这是研究框架，不是任何厂商官方的「七层」。

[指向核心能力 7 层图] 从下往上看：**状态与恢复**——恢复什么、哪些动作会重跑；**运行基础设施**——隔离、容量、网络与生命周期；**工具与上下文**——模型、知识、记忆、业务动作怎么接；**Harness 与编排**——谁控制循环、子任务、流程与审批；**定义与资产**——定义、工具、技能、模型怎么复用和版本化；**产品接入**——谁能调用、怎么接渠道。**治理与运营**横跨所有层：身份、权限、质量、发布、审计、费用。

每一层上我们都标注了两家产品对应的组件——这就是两套架构的「共同骨架」。用它做两件事：选型时的验证清单，自建时的分层设计底稿。

体系之外还有三块**不属于平台本体**的外部依赖：模型推理基础设施、企业业务系统、知识摄取管道——它们要单独设计，不要让平台的「一体化」叙事掩盖掉。

Amazon 官方自己也有一个七维韧性模型（模型、编排、基础设施、知识库、工具、安全、评估）——和「初始七项服务」是两个概念，看官方材料时注意区分上下文。

## 收尾（约 1 分钟）

总结：阿里云和 Amazon 给出了同一个命题的两种解法——统一组织，还是可组合运行。没有绝对优劣，取决于你的起点：已有云上资产、要统一治理，还是已有 Agent 代码、要接入运行环境。
