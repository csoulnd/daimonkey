评分方法论 {{ meta.methodology_version }}

1. 双分设计

每个有足够公开数据的产品计算两个 0-100 分：

  • 热度分（heat_score）：存量规模。Stars、下载量、安装量、贡献者、Forks 的加权组合。
  • 动量分（momentum_score）：近期增长。30 天提交、30 天发布、各指标 30 天增长率。

双分的理由：小体量高速增长的项目（提交密集、新发布频繁）会被单看存量的榜单系统性低估。

2. 归一化：分类内分位数

norm(x) = 指标 x 在同一榜单已观测产品中的分位数排名（0-1，并列取平均位次）
heat_score     = 100 × Σ wᵢ · norm(指标ᵢ)      其中 Σ wᵢ = 1
momentum_score = 100 × Σ wᵢ · norm(增长ᵢ)

用分位数而非原始值：Stars 是 10⁵ 量级、VS Code 安装量是 10⁷ 量级，直接加权会被大量纲指标吞掉。 方向指标（App Store 榜单名次）在归一化时反转（名次越小越强）。

增长项先用平滑基数计算相对增长，再与绝对新增各取一次分位，两者各占增长项的一半。 Stars 的平滑基数为 100，下载量为 1000；npm 绝对新增由月下载量与官方增长率估算，缺少估算条件时绝对项取中性分位。

3. 联合榜单（数据整合）

联合榜只采用产品的主分类（编码 / 框架 / 通用 / Claw），先计算分类综合分， 再将该综合分在本分类已入榜产品中做第二次分位排名。同一产品只出现一次； 国产开源榜和国产应用榜是地域专题榜，不重复计入联合榜。

联合榜衡量产品在所属赛道中的相对位置，不表示跨赛道绝对体量。分类样本较少时分位数较粗， 可下钻查看原始指标和覆盖率。

4. 缺失值处理

  • 某产品缺某指标 → 该指标赋中性分位 0.5，并计入覆盖率缺口；真实零值参与分位排名；
  • 某指标整榜缺失 → 该指标从本榜剔除、权重重归一化（整榜口径变化会体现在页面与 API 的 weights 字段）；
  • 热度覆盖率 = 已有指标生效权重 / 本榜生效权重；低于 50% 进观察区。动量可用权重低于 50% 时不显示动量分；
  • 未注册分发渠道的产品不把下载量计为零；无公开仓库的闭源产品会进入观察区，现阶段不以推测值补齐；
  • 动量的增长类指标依赖本站自采历史（npm 例外，官方 range API 可回溯），上线初期动量分以 30 天提交/发布为主，约 30 天后完整。

6. 数据溯源（本项目核心）

三级视图逐级下钻：榜单 → 产品指标时序 → 原始 HTTP 响应。 任何展示的原始指标都带来源、采集时间与原始数据链接（数据库层面 metrics.raw_payload_id 强制非空）。 综合分是计算结果，可从各指标和方法版本复算。
